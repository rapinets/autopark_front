# Спільні правила специфікацій

Цей файл читається разом із кожною spec. Версія 1.0, 17.11.2026. Продуктові вимоги походять із розділів 1–5 та наступного запиту про ітерації. Візуальна система, збереження параметрів у hash і картки додаткових сутностей — запропоновані рішення цього пакета; їх можна змінити до реалізації з оновленням відповідних критеріїв.

## Стек і структура реалізації

HTML, CSS, JavaScript без React/Redux. Рекомендація: ES modules, Fetch API, CSS variables, hash-router. API_BASE_URL налаштовується в одному місці. Не зберігати секрети в браузерному конфігу. Запуск через HTTP, не file://.
Рекомендовані модулі: api/client.js, api/_ для сутностей, router.js, pages/_, components/\*, utils/validation.js, styles/tokens.css і styles/components.css. Це орієнтир, не вимога створювати порожні файли.

## Дизайн-система DS-01

- Світла адміністративна панель: фон #F8FAFC, поверхні #FFFFFF, текст #0F172A, другорядний текст #475569, основна дія #0F766E, небезпечна дія #B91C1C, межі #CBD5E1. Стани відрізняються також текстом/іконкою.
- Системний шрифт без обов’язкового зовнішнього завантаження; основний текст 16 px, міжрядковий інтервал 1.5, заголовки 24–32 px.
- Відступи 4/8/12/16/24/32 px, скруглення карток 12 px; стримана тінь, без декоративних графіків або випадкових фотографій.
- На desktop від 1024 px — sidebar 240 px; контент до 1280 px. На меншій ширині — компактна верхня навігація з доступним меню. Відступ контенту 16 px на мобільному, 24–32 px на великому екрані.
- Таблиці на ширині <768 px стають картками з підписаними значеннями. Дані й дії не зникають. Горизонтальної прокрутки всієї сторінки від 360 px немає.
- Кнопки й основні цілі натискання не менші 44×44 px; контраст звичайного тексту не менше 4.5:1, видимий focus. Колір не є єдиним носієм значення.
- Рух 120–180 ms за потреби; враховувати prefers-reduced-motion. Лоадер не має нескінченно маскувати помилку.

## Базова поведінка G-01–G-09

G-01. Кожен список: loading, empty, error із повтором GET, data. Деталі: loading, not-found, error, data. Пошукова порожнеча відрізняється від порожньої БД.
G-02. Усі тексти користувача/API/detail відображаються через textContent/value або еквівалентно безпечно; не вставляти їх у innerHTML. В API передавати звичайні trim-значення, не HTML-сутності.
G-03. Всі форми перевіряються перед запитом. 422: loc → поле, msg → повідомлення; невідомі й загальні помилки не губляться. Не показувати raw JSON або стек у UI.
G-04. Під час мутації заблокований повторний submit. Невдача зберігає введення. Успіх очищає/закриває форму тільки після підтвердження сервера.
G-05. Якщо POST успішний, але GET після нього неуспішний, показати «Збережено, але не вдалося оновити дані». Повторювати GET, не POST.
G-06. 204 обробляти без response.json(). 404/409 показувати через detail, загальний 409 не вважати автоматично дублікатом конкретного поля.
G-07. Застарілі відповіді не перезаписують нову сторінку/пошук/сутність. Використати скасування читання або ідентифікатор запиту. Скасування браузерного запиту мутації не гарантує скасування операції сервером.
G-08. Labels, клавіатурна навігація, повідомлення доступні допоміжним технологіям. Після переходу оновити document.title й фокус заголовка; після діалогу повернути фокус до ініціатора.
G-09. Підтвердження потрібне лише для видалення водія і скасування допуску; звичайні читання й збереження не вимагають додаткового діалогу.

## Контракт API

Це ціль інтеграції, не підтвердження, що користувач уже встановив усі виправлення. Використовувати точні шляхи зі свіжої OpenAPI, включно з кінцевими слешами.

| Операція                 | Шлях                                | Відповідь                                         |
| ------------------------ | ----------------------------------- | ------------------------------------------------- |
| GET / POST перевізників  | /companies/                         | Company[] / Company, 201 для POST                 |
| GET перевізника          | /companies/{id}                     | Company                                           |
| GET / POST автобусів     | /buses/                             | Bus[] / Bus, 201 для POST                         |
| GET автобуса             | /buses/{id}                         | Bus                                               |
| GET / POST маршрутів     | /routes/                            | Route[] / Route, 201 для POST                     |
| GET маршруту             | /routes/{id}                        | Route                                             |
| GET / POST водіїв        | /drivers                            | Driver[] / Driver, 201 для POST                   |
| GET / PUT / DELETE водія | /drivers/{id}                       | Driver / Driver / 204                             |
| GET допусків водія       | /drivers/{id}/routes                | [{driver_id, route_id}], за number маршруту       |
| POST допуску             | /assignments                        | {driver_id, route_id}, 201                        |
| DELETE допуску           | /assignments/{driver_id}/{route_id} | 204                                               |
| GET стану                | /health                             | 200, {"status":"ok"}; доступність API, не тест БД |

Company: id, name, phone. Bus: id, plate_number, model, seats, company_id, company_name. Route: id, number, title, distance_km. Driver: id, full_name, phone, license_number, company_id, company_name. Вхідні ID — додатні цілі. GET водіїв: limit 1–100, offset ≥0; загального total немає. Списки companies/buses/routes у наданому коді непагіновані.

PUT водія вимагає full_name, phone, license_number, company_id. company_name та id не передаються як редаговані поля. Деталі допуску отримувати зіставленням route_id з id загального каталогу маршрутів, не множиною індивідуальних запитів.

## Валідація V-01

Усі вхідні текстові поля trim перед перевіркою довжини. Внутрішні пробіли зберігаються. Поля створення обов’язкові; текстові обмеження рахують символи, не байти. Для Unicode бажано узгодити підрахунок кодових точок із сервером (наприклад Array.from(value).length).

| Сутність   | Правила                                                         |
| ---------- | --------------------------------------------------------------- |
| Company    | name 2–120; phone 7–20                                          |
| Bus        | plate_number 4–15; model 2–80; seats ціле 10–120; company_id >0 |
| Route      | number текст 1–10; title 3–120; distance_km ціле 1–5000         |
| Driver     | full_name 3–120; phone 7–20; license_number 5–20; company_id >0 |
| Assignment | driver_id >0; route_id >0; обидва цілі                          |

Порожнє число не перетворювати на 0; дробові не округлювати; parseInt не має приховувати некоректне введення. Телефон — рядок; regex +380, формат номерного знака й автоматичний uppercase не задані.

## Зразки даних для перевірки

Наданий seed: 5 перевізників, 10 автобусів, 10 маршрутів, 10 водіїв, 20 допусків (лише для чистої БД після одноразового імпорту). Окремий тестовий набір: 0/1/10/11/20/21/50/51 водіїв; однакові ПІБ; довгі назви; водій без допусків і з усіма маршрутами; граничні значення; текст із HTML. Не змінювати робочі дані заради тестів.

## Рекомендації до ведення specs

- Критерії Sxxx-AC-yy зв’язувати з перевірками й задачами; зберігати короткий журнал результатів.
- Перед інтеграцією зафіксувати версію OpenAPI. Зміна контракту повинна оновити цей файл і залежні ітерації.
- Не дублювати спільні обмеження в кожному компоненті: один модуль валідації й один API-клієнт.
- Не додавати статистичні ендпоінти без окремої домовленості. 007 містить варіанти рішення.
- Рекомендовані автоматизовані перевірки: валідація меж, алгоритм P+1, множина, 204/422 та кілька наскрізних сценаріїв. Візуальні зміни перевіряти на контрольних ширинах.
- Наприкінці ітерації зазначати «перевірено на реальному API», «на тестових даних» або «не перевірено». Mock не доводить роботу MySQL.

## Загальне визначення готовності

Критерії поточної spec виконані; перевірені позитивний і негативний сценарії; 360 px і клавіатура; немає необроблених помилок консолі; попередні функції працюють; API-відхилення записані, а критичні закриті. Наступна ітерація не є місцем виправлення відомих критичних дефектів поточної.
