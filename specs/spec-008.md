# SPEC-008 — Повна перевірка помилок і відновлення

Статус: Реалізовано для перевірки. Залежності: 004–007. Мета: однакова й передбачувана поведінка при помилках на всіх екранах. Базові стани вже реалізовані раніше; тут їх перевіряють наскрізно та усувають прогалини.

## Матриця поведінки

| Ситуація | Очікувана реакція |
|---|---|
| GET деталей → 404 | «Запис не знайдено», повернення до списку |
| POST/PUT → 404 | detail, введення зберігається; не вгадувати відсутню сутність |
| 409 з бізнес-повідомленням | detail; поле позначається лише за однозначно відомою причиною |
| Загальний IntegrityError 409 | «Порушено цілісність даних» на рівні операції |
| 422 | loc/msg біля поля; невідомий loc або query-помилка — загальне повідомлення |
| 5xx / неочікуване тіло | Зрозуміла помилка сервісу, без raw HTML/стека |
| Мережевий збій / timeout | Окреме повідомлення; GET можна повторити |
| Успіх мутації + помилка читання | Підтвердити збереження й запропонувати повтор GET |
| Невизначений результат мутації через мережу | Не повідомляти однозначно «не збережено»; запропонувати актуалізувати дані перед повторною дією |

Не називати будь-яку мережеву помилку «сервер вимкнений»: причиною може бути CORS або зв’язок. Запропонований timeout 15 с налаштовується централізовано. Автоматичних повторів POST/PUT/DELETE немає.
Скасування застарілого GET при навігації не показувати як аварію користувачу. Не втрачати введення через фонове оновлення. Повідомлення на новому екрані не має стосуватися попереднього запису.

## Дизайн

Спільні error-summary над формою, inline-помилки під полями, банер проблеми читання з кнопкою повтору. Повідомлення про успіх не перекриває поля та не є єдиним місцем, де можна побачити результат. Для помилки — достатній час читання; вона не зникає автоматично до виправлення/нової дії.

## Задачі

- [x] Додано обробку 404/409/422/5xx/мережі/timeout і захист stale-відповідей.
- [ ] BR-B1–BR-S1 перевірені частково на mock/реальних GET; реальні мутації й каскад лишаються неперевіреними.
- [x] Додано тестові затримки, помилки та stale-кейс у тестовому середовищі.
- [x] Перевірено безпечне textContent-виведення HTML-подібного рядка.

## Критерії приймання

- S008-AC-01: 404/409/422/5xx/мережа оброблені відповідно до матриці; немає необроблених Promise rejection.
- S008-AC-02: після помилки поля збережені, кнопка знову доступна; 422 має доступний зв’язок із input і фокус першої помилки.
- S008-AC-03: затримана відповідь попереднього ID/сторінки не змінює поточний екран; скасований GET не дає зайвого банера.
- S008-AC-04: при одночасному додаванні/скасуванні допуску іншим клієнтом конфлікт коректно відображається й список актуалізується.
- S008-AC-05: у name/full_name/title/detail рядок <img src=x onerror=alert(1)> показаний як текст; нічого не виконується.
- S008-AC-06: загальний 409 не прив’язаний безпідставно до телефону чи посвідчення; спеціальний BR-B2 відповідає ТЗ на реальному API.
- S008-AC-07: після timeout мутації немає автоматичного повтору або безумовного повідомлення про невдачу; доступне актуалізування даних.

Готовність: матриця пройдена; відхилення бекенду записані й критичні усунені, а не замасковані клієнтом.
