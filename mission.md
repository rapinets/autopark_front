# Місія — вебінтерфейс обліку пасажирських перевезень

Версія пакета: 1.0 • 17.11.2026 • Статус: план реалізації, не звіт про готовий фронтенд.

## Мета

Створити зрозумілий вебінтерфейс, у якому працівник автопарку веде облік перевізників, автобусів, маршрутів, водіїв і допусків водіїв до маршрутів через наявний REST API. Базова адреса: https://autopark-back.onrender.com

## Очікуваний результат

Застосунок на HTML, CSS і JavaScript з узгодженим сучасним дизайном, який дозволяє:

- переглядати списки всіх основних сутностей і допуски конкретного водія;
- відкривати детальну картку перевізника, автобуса, маршруту й водія;
- створювати перевізників, автобуси, маршрути й водіїв;
- редагувати та видаляти водіїв;
- додавати й скасовувати допуски;
- бачити загальні лічильники та стан API;
- працювати з телефону від 360 px і з комп’ютера;
- розуміти результат кожної операції та виправляти помилки без втрати введення.

## Користувач і основні задачі

Основний користувач — працівник, відповідальний за актуальність даних перевезень. Він знаходить запис, перевіряє деталі, додає або змінює доступні дані, керує допусками та отримує підтвердження результату.
Ролі, логін і права доступу не визначені вихідними вимогами; окремий модуль авторизації не входить до цього пакета.

## Межі продукту

Фронтенд відповідає за UI, навігацію, клієнтську валідацію, HTTP-запити та повідомлення. Бекенд — за MySQL, остаточну перевірку правил, унікальність і транзакції.

У поточному API редагування/видалення є лише для водія; для допуску доступне скасування. Кнопки зміни інших сутностей не створювати без розширення контракту.

Детальні картки перевізника, автобуса й маршруту — розширення первинного переліку екранів на основі поточного запиту користувача; відповідні GET є в наданому бекенді. Допуск не має власного ID та окремої картки: він відображається в картці водія.

Поза обсягом: рейси, квитки, пасажири, GPS, аналітичні графіки, експорт, призначення автобуса на маршрут, глобальний пошук водіїв, редагування перевізників/автобусів/маршрутів.

## Принципи

1. Кожна ітерація дає видимий і перевірюваний результат.
2. Дизайн розвивається на спільних компонентах і токенах.
3. Базові помилки, доступність і безпечне виведення потрібні з першого запиту; окрема пізня ітерація поглиблює перевірки.
4. Очікування API не вигадуються: непідтверджені можливості зазначені як залежності.
5. Стан «готово» означає виконані критерії, а не лише написаний код.

## Успіх

Усі критерії spec-001–spec-009 виконані й перевірені на погодженому бекенді. README описує запуск і конфігурацію. Фронтенд не видає помилку за успіх, невідоме число за нуль або локальний пошук за глобальний. На ширині 360 px доступні всі основні операції.
